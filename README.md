# Passage Beta Dashboard

Passage 베타테스터의 미션 수행 현황을 관리 업체 담당자가 웹에서 확인하는 대시보드입니다.

> 테스터는 Passage 앱에서 활동하고, 관리 업체는 웹에서 진행 상황을 확인한다.

테스터가 앱에서 남긴 활동 기록을 기존 Passage Supabase DB에서 자동 집계해 보여줍니다. 담당자가 테스터 활동을 일일이 확인하거나 수동으로 기록하지 않아도 되게 하는 것이 목적입니다.

## 재생 기록 관리 (계획)

> 아직 만들기 전입니다. 요구사항은 Passage 저장소의 `docs/tasks/active/TASK-031-playback-admin-web.md` 에 있습니다. 앱에서 재생 기록을 모으는 부분(TASK-030)은 끝났습니다.

Passage 앱이 모은 **재생 기록**을 관리자가 웹에서 봅니다. 어떤 재생을 셀지 조건을 바꿔 가며 횟수를 계산해 보고, 결과를 CSV·Excel 파일로 받습니다. KOMCA와 글로 합의한 기준이 생기면, 그 기준만 적용한 정산 보고서를 만듭니다.

### 숫자를 다루는 원칙

| 구분 | 뜻 | 다루는 방법 |
| --- | --- | --- |
| 실제 재생 기록 | 앱이 보낸 기록 그대로 (재생 1번 = 1줄) | 어떤 조건을 골라도 고치지 않는다. 실제 횟수는 항상 보인다 |
| 계산해 보기용 조건 | 관리자가 골라 보는 조건 | KOMCA와 협의하기 전에 숫자를 비교해 보는 용도. 실제 정산에는 저절로 들어가지 않는다 |
| 정산 기준 (KOMCA 합의) | KOMCA와 합의한 조건 | KOMCA 보고서에는 이것만 쓴다 |

- 재생 하나가 여러 조건에 걸려도 **한 번만 뺀다**. 한 곡에 저작자가 여러 명이어도 횟수가 불어나지 않는다.
- 기록이 부족해 판단할 수 없는 재생은 마음대로 넣거나 빼지 않고 **"확인 필요"로 따로 보여준다**.
- 데이터는 관리자만 쓸 수 있는 조회 함수 `playback_session_facts(p_from, p_to)` 에서 가져온다. 비밀 키(service role)는 브라우저에 두지 않는다.

### 셀지 뺄지 고르는 조건 (조건마다 따로 고른다)

| 화면에 보이는 이름 | 무슨 경우인가 | 판단에 쓰는 값 (개발용) |
| --- | --- | --- |
| 자기 녹음을 직접 들은 것 | 녹음을 올린 사람이 자기 녹음을 재생 | `is_own` |
| 같은 게시글 안에서 다시 들은 것 (**기본: 빼기**) | 게시글을 나가지 않은 채 같은 녹음을 다시 재생. 끝까지 듣고 다시 재생, 댓글 시간을 눌러 다시 재생, 이 곡의 기록 시트에서 같은 녹음 다시 미리 듣기 모두 해당. 앞 재생의 끝 기록이 빠졌어도 확인 필요로 두지 않고 뺀다 | `prev_relation = same_visit` (`prev_end_type` 과 상관없이) |
| 나갔다 다시 들어와서 들은 것 | 게시글을 나갔다가 다시 들어와 재생 | `prev_relation = reentry_same_post` |
| 짧은 시간 안에 또 들은 것 | 같은 사람이 같은 녹음을 정한 시간(2·5·10·30·60초) 안에 다시 재생. 시간은 "앞 재생을 시작한 때", "앞 재생이 끝난 때", "게시글을 나간 때" 중 하나부터 잰다 | `gap_start_to_start_ms` / `gap_end_to_start_ms` / `gap_exit_to_reenter_ms` |
| 어디서 들었나 | 게시글 화면 / 이 곡의 기록 시트(곡 이름 옆 "N번째 도전" 칩을 누르면 뜨는 시트, 같은 사람의 이전 게시글을 ▶로 미리 듣는 곳, 서버 스트리밍) 중 고른 곳에서 들은 것만 센다 | `source` |
| 멈췄다가 이어 듣기 | 일시정지 후 다시 재생. 항상 같은 재생 1번 (확정, 고르는 조건 아님) | 같은 재생 안의 `pause`·`resume` |

그 밖의 표시:

- **휴대폰 시계가 어긋난 재생**: 서버 시각과 5분 넘게 차이 나는 재생을 따로 표시한다. 횟수에는 영향이 없다 (`start_clock_offset_ms`).
- **날짜 기준**: 앱에서 재생한 시각(`started_at`)과 서버가 받은 시각(`received_at`) 중 고른다.

### 재생 횟수 세는 기준 (2026-10-30 결정)

자세한 근거와 전체 시나리오 검토는 Passage 저장소 TASK-031 "재생 횟수 세는 기준"에 있다.

| 경우 | 횟수 |
| --- | --- |
| 처음 재생 (1초라도 재생되면) | 1 |
| 일시정지 → 댓글 보기 → 댓글 시간 누르기 | 그대로 1 (같은 재생 안에서 위치만 이동) |
| 재생 중 댓글 시간 누르기, 파형 이동, 댓글 쓰기·수정 | 그대로 1 |
| 끝까지 듣고 같은 게시글 안에서 다시 재생 | 그대로 1 (다시 재생은 뺀다) |
| 앞 재생의 끝 기록이 빠진 채 같은 게시글 안에서 다시 재생 | 그대로 1 (확인 필요가 아니라 뺀다) |
| 강제 종료 등으로 끝 기록이 없는 재생 | 1 (재생 시작이 있으면 센다) |

- 댓글 시간 탭은 따로 구분하거나 수집하지 않는다.
- **1초라도 재생되면 1번으로 센다 (KOMCA 기준).** 들은 시간으로 빼는 조건("너무 짧게 들은 것")은 두지 않는다.
- **승인 전 계정 조건은 두지 않는다.** 승인 안 된 계정은 커뮤니티에 들어올 수 없다.
- 아직 정하지 않은 것: 확인 필요 재생을 정산에서 어떻게 할지. 확인 필요는 두 경우에만 생긴다: "짧은 시간 안에 또 들은 것"을 켰는데 앞 재생의 끝 시각이 없을 때, "자기 녹음"을 켰는데 올린 사람인지 알 수 없을 때.

### 화면

1. **재생 현황** (`/playback`, **구현됨 — 예시 데이터**): 제외 기준을 켜고 끄면 정산 대상 · 전체 재생 · 제외 · 확인 필요 숫자와 곡별/녹음별 표가 바로 바뀐다. 표는 5줄까지 보이고 나머지는 "더보기 / 접기". 지금 보이는 표를 CSV로 받을 수 있다. 계산은 `src/lib/playback.ts` 한 곳에서만 한다.
2. **재생 기록** (`/records`, **구현됨**): 그 달 재생된 녹음 목록 → 녹음 하나를 고르면 들은 사람(가명 ID)별로 방문마다 흐름(들어옴 → 재생 → 일시정지 → 끝까지 들음 → 나감)과 재생별 결과(셈 / 뺌 / 확인 필요와 이유)를 보여준다. 재생 현황의 녹음별 표에서 녹음을 눌러도 온다. DB 함수 `monitor_playback_timeline` 이 필요하다 (`supabase/monitor_playback_timeline.sql`).
3. **정산 · 파일** (`/settlement`, **구현됨**): 지금 쓰는 제외 기준(재생 현황에서 고른 것), 예상 계산안(정산 대상 재생 수 × 단가, 단가는 환경 변수 `NEXT_PUBLIC_ESTIMATE_WON_PER_PLAY`, 곡별 5줄 + 더보기), CSV 받기(곡별 / 녹음별 / 재생 하나씩). 저장한 조건 목록과 Excel(.xlsx)은 아직 없다. KOMCA 보고서는 정산 기준을 등록해야 만들 수 있다. 등록 전에는 어떤 숫자도 "정산 확정"으로 표시하지 않는다.

실제 DB 연결은 아직 없다. 관리자 확인이 들어간 DB 함수(`playback_session_facts` 를 감싸는 것)가 먼저 필요하고, 이는 관리자 목록 설계(TASK-001)에 걸려 있다.

아직 정하지 않은 것(관리자 로그인 방식, 조건 저장·잠금, 파일에 넣을 항목, KOMCA 보고서 양식)은 TASK-031 "결정 필요" 항목을 따른다.

### 사용자가 정하지 않았는데 시안·문서에 들어간 것 (Claude가 추론하거나 임의로 정함)

아래는 사용자 결정이 아니다. 시안을 그리려고 넣은 값이며, 바꾸거나 지워도 된다.

| 항목 | 지금 들어간 값 | 근거 |
| --- | --- | --- |
| 이 곡의 기록 시트에서 ▶로 미리 들은 것 | 기본 **셈** | 임의. **결정 필요** — 셀지 뺄지 사용자 답변 대기 |
| 자기 녹음을 직접 들은 것 | 기본 빼기 | 임의 (요구사항은 "포함/제외 선택"만 있음) |
| 나갔다 다시 들어와서 들은 것 | 기본 셈 | 임의 |
| 짧은 시간 안에 또 들은 것 | 기본 켬, 10초, "앞 재생이 끝난 때부터" | 임의 예시값. 시간 후보(2·5·10·30·60초)와 기준 3가지는 요구사항 6장 |
| 확인 필요 재생 | "정산 대상"에 넣지 않음 | 임의. 정산에서 어떻게 할지 미결정 |
| 휴대폰 시계 어긋남 기준 | 5분 | TASK-030 설계의 구현 제안값 |
| 화면 3개 구성, 메뉴·조건 이름 | 시안대로 | Claude 제안 (결정 필요 3) |
| 재생 현황 표에 "확인 필요" 칸 추가 | 정산 대상 + 제외 + 확인 필요 = 전체 재생이 되도록 | 구현하면서 Claude가 더함 (시안에는 없었음) |
| 예상 계산안 = **정산 대상** 재생 수 × 단가, 0.1원 단위 | 시안·계산 함수에 반영 | 단가는 사용자 지정 (저장소에 두지 않고 환경 변수로). "정산 대상"을 곱하는 것과 반올림 단위는 Claude가 정함 |
| 받기 파일 형식 | 지금은 CSV만 (엑셀에서 열림) | Claude가 정함. Excel(.xlsx)은 아직 없음 |
| 제외 기준 저장 | 없음. 고른 기준은 재생 현황 → 정산 · 파일로 따라가지만 새로고침하면 기본값 | Claude가 정함 (저장할 DB가 아직 없음) |
| 예상 계산안의 빠진 금액 | 제외와 확인 필요를 나눠 보여 줌 (시안은 한 줄) | Claude가 정함 |

| 정산 기준 등록 후 잠금·변경 이력 | 시안에 그림 | Claude 제안 (결정 필요 5 미정) |
| 파일 항목, 들은 사람 가명 ID 넣기 | 시안에 그림 | Claude 제안 (결정 필요 4 미정) |
| 관리자 로그인 | 이메일 + 비밀번호 관리자 계정 따로 (`monitor_admins`) | 방식 A는 사용자 결정 (2026-10-30). 표·함수 이름, 조회 기간 필수·최대 93일은 Claude가 정함 |

## 현재 상태

재생 현황 화면을 예시 데이터로 구현했습니다 (DB 연결 전). 자세한 현황은 [docs/PROGRESS.md](docs/PROGRESS.md) 를 보세요.

## 주요 기술

Next.js 16 (App Router) · TypeScript · Tailwind CSS v4 · Supabase (기존 Passage 프로젝트) · Vitest · Vercel

## 개발 시작

Node.js 22 이상이 필요합니다.

```bash
npm install
cp .env.example .env.local   # Passage Supabase URL / anon key 입력
npm run dev                  # http://localhost:3000
```

검증 명령(`lint`, `typecheck`, `test`, `build`)은 [docs/VERIFICATION.md](docs/VERIFICATION.md) 에 정리되어 있습니다.
